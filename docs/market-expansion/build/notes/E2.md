## Decisions

### E2-1 — The S09 confidence basis is stored as an evidence claim on the assumption
- Context: `assumptions.create.sourceIds` (D-132) needs a link from an assumption to its sources. Migration 0006 adds
  no assumption–source table, and `AssumptionVersion.sources` was always empty.
- Decision: one accepted, human-authored `platform.claim` per assumption with `kind = 'evidence'`,
  `kind_detail = 'assumption_basis'`, `assumption_id` set and **`case_id` NULL**, plus one `claim_evidence_link`
  (`supports`) per source (`modules/me/assumptions/evidence.ts`). The register reads them back as source chips
  (metadata only, restricted flag from the viewer's entitlement). `case_id` is NULL so the link never shows up as a
  thesis claim (S05 lists claims by case).
- Alternatives: a new table (needs a migration; proposed as CR-E2-1); free text in `basis` (not linkable, no chips).
- Consequences: lineage "used by" for these sources does not see the link (it reads claims with a case id). A
  version change keeps the same basis sources (the link is per assumption, not per version).

### E2-2 — Evidence quality on create is the strongest linked source; hidden sources are refused alike
- Decision: the version's `evidence_quality` is the best chip quality of the linked sources (licensed → Strong,
  authorized upload / internal → Some, public web → Weak — the existing `sourceChips` mapping); no source →
  `none` ("Assumption — no evidence"). A source the author cannot open (restricted licence, deleted, another
  tenant, unknown id) is refused with the same `VALIDATION_FAILED` "Link a source you can open." (never-rule 8: no
  difference between hidden and missing). Money units take the editor's `currency` / `priceYear`, else the case's
  sizing boundary (unchanged fallback).

### E2-3 — Stop-rule trips: who reports, one open trip per rule, the sponsor is asked
- Decision: `pilot.tripStopRule` loads the rule from the **approved G2 snapshot** of the plan's gate (statuses
  approved, approved with conditions, invalidated, expired); anything else is 404. Reporters: the rule's owner, or a
  role with `pilot.edit_plan` (case owner, pilot owner); agents and services are refused (`auth: human`). The only
  write is a `platform.review_request` (area `sponsor`, target `stop_rule`, `target_id` = rule id, reviewer = the
  case sponsor, question "SRn tripped: <trigger>. Review the pilot and decide what happens next.", what-to-check =
  the pre-registered consequence and the evidence) and the audit event `stop_rule.tripped`. A second trip while that
  review is open is `INVALID_TRANSITION`; after the sponsor answers, the rule can be reported again. No analytics
  event (PRD §17 lists none). The DB test asserts plan, task, gate, approval and stage rows are byte-for-byte the same
  before and after (never-rule 7).

### E2-4 — Record spend: remaining is per kind, net of reversals; corrections are reversals only
- Decision: `budget.recordEntry` refuses an amount above `approved − net(kind)` (spent and committed are each capped
  at the approval, as before) with `PRECONDITIONS_UNMET`, title "This would exceed the approved €120k. Request a
  scope change." and blocker `budget_ceiling` whose message names the remaining amount and whose `href` is
  `/me/cases/<key>/pilot?view=scope` (S11 opens the scope-change dialog). A zero amount is refused. `taskId` must be
  a task of the case. `budget.reverseEntry` appends a row with the same gate, kind, amount, currency, reference and
  task, `as_of` = tenant-local today, `source_text` "Reversal of …" and the reason; it refuses a second reversal and a
  reversal of a reversal before the database guard does. The meter (`pilot.get`, `budget.listEntries`) subtracts
  reversals; rows stay non-negative one-time money and are never shown next to a `/year` figure.
- `budget.listEntries` defaults to the gate that authorizes the pilot plan; its meter is null until that gate is
  decided (same rule as S11). Read access: anyone who can read the case.

### E2-5 — Plan editor: ordinals, budget lines inside the ceiling, sent or spent tasks stay
- Decision: `pilot.saveDraft` (now in `modules/me/pilot/draft.ts`) resolves `milestoneOrdinal` against the
  milestones after the milestone part of the same patch, and `dependsOnOrdinals` against task positions in the patch;
  ids win when given. Unknown ordinals are 400; unknown ids are 404 (a milestone id not in the plan used to be
  inserted as a new row silently). A task budget line must be in the plan's currency; all lines together must stay
  within the plan version's budget ceiling; an absent `budgetLine` keeps the stored line, `null` clears it. A task with
  recorded spend cannot be removed (like a sent task). Milestone `dueOn` / `evidenceExpected` absent keep, null clears.

### E2-6 — S07 add dimension
- Decision: `feasibility.addDimension` (policy `review.request`) refuses a dimension already on the case (409), and a
  reviewer who is not an active human member of the case (role reaching the case other than tenant admin,
  participant, owner or sponsor — the `cases.members` rule) with 400 on `body.reviewerId`. It stores the row
  `in_review` with the scope of review in `scope_text` (replaced by the signed scope on sign-off), `question_detail`,
  and `human_only` forced on for the specialist review; it also creates the reviewer's review request (area by
  dimension, target `feasibility.<dimension>`, `target_id` = the assessment) so the reviewer is asked in Reviews.
  `FeasibilityAssessment.questionDetail` now prefers the stored `question_detail`.
- The "AI may draft the question" path (existing `feasibility_question` proposal) is not wired into the new form.

### E2-7 — UI label maps the contracts do not have
- S09 uses local display text for value units and for the model inputs it offers (`adoption_rate.*`,

## Workflow updates

- **WF-07 (pilot activation → outbox)**: before activation the S11 "Edit plan" form edits milestones (date, evidence
  expected) and tasks (incl. one-time budget lines) of the draft; activation unchanged. After activation: "Record
  spend" (append-only; correction = reversal with a reason; above the remaining amount → "Request scope change" →
  `pilot.requestScopeChange`, which already runs materiality) and "Stop rules · pre-registered" → "Report trip" →
  sponsor review item. New failure paths: `PRECONDITIONS_UNMET budget_ceiling`; `INVALID_TRANSITION` for a second
  reversal / reversal of a reversal / a second open trip; 404 for a stop rule not in the approved snapshot.
- **WF-05 (assumption register)**: "Add assumption" creates version 1 with its confidence basis; Evidence vs
  "Assumption — no evidence" drives the register group as before.
- Feasibility (no WF): "Add dimension" → review request to the named reviewer → `feasibility.sign` unchanged.
