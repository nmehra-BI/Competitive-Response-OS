## Decisions

### E5-1 · The key is written atomically at create; read back, not re-PUT
- **Context:** WAVE4 says "create the issue, then set the issue entity property". Setting an issue
  property with `PUT /issue/{key}/properties/{p}` needs the **Edit issues** permission, which D-121
  deliberately does not grant (Browse, Create, Assign only).
- **Decision:** `POST /issue` carries `properties: [{ key: 'growth-os.idempotency', value: { key } }]`
  and the label `growth-os-key-<key>` in the same request (atomic). Before reporting success the
  adapter reads the property back (Browse only). Only if Jira dropped it does it PUT it; a 403 there is
  accepted because the label, written atomically, is the reconcile handle. Any other failure after the
  create is `timeout_ambiguous` → reconcile.
- **Alternatives:** create then PUT (needs Edit issues — widens the account); label only (no proof).
- **Consequences:** "the key is on the issue before success is reported" holds with the minimal
  permission set; one extra GET per create.

### E5-2 · Reconcile searches by label and confirms by property
- **Context:** issue entity properties are JQL-searchable only when an app *indexes* them (Connect or
  Forge descriptors). A 3LO app cannot, so `issue.property[growth-os.idempotency].key = …` would not
  find anything on real Jira.
- **Decision:** `findByIdempotencyKey` runs `POST /rest/api/3/search/jql` with
  `project in (<mapped projects>) AND labels = "growth-os-key-<key>"`, then reads each hit's property;
  a hit whose property names another key is ignored. `createTask` runs the same search in the task's
  project before creating (idempotent by key).
- **Consequences:** the mapped-project clause keeps reads inside the mapped projects (D-121 §5). Jira's
  search index can lag a create by seconds; the outbox only searches after a timeout or on retry, and a
  missed hit there would mean one possible duplicate — documented as a known gap (Status).

### E5-3 · When is `jira_cloud` served
- **Context:** D-135 says `TASK_CONNECTOR=jira` registers `jira_cloud`. The API, the worker and the e2e
  harness are separate processes; the real-stack Playwright config starts the shared worker with
  `TASK_CONNECTOR=simulated` hard-coded. A process that does not serve `jira_cloud` turns every send
  for such a connection into `unavailable`, which pauses the tenant's Jira connection.
- **Decision:** `jira_cloud` is served when `TASK_CONNECTOR=jira` **or** when the complete Jira
  configuration (`JIRA_CLIENT_ID`, `JIRA_CLIENT_SECRET`, `CONNECTOR_TOKEN_KEY`) is present. With
  `TASK_CONNECTOR` unset/simulated and no Jira configuration, behaviour is unchanged (the simulated
  connector is the default; `jira_cloud` → always-unavailable adapter). An incomplete configuration
  with `TASK_CONNECTOR=jira` gives an unavailable adapter naming the missing variable (never a value),
  and `admin.createConnection` answers 503 `CONNECTOR_UNAVAILABLE`.
- **Alternatives:** strict `TASK_CONNECTOR=jira` only (then the e2e needs a PE edit to
  `playwright.real.config.ts`; see CR-E5-3).
- **Consequences:** an operator can switch Jira on per deployment with the secrets alone; the default
  stays simulated. PE may tighten this back to strict once CR-E5-3 lands.

### E5-4 · Tenant resolution for the credential (RLS)
- **Context:** `platform.connection_credential` is RLS-forced; the factory receives only
  `{ id, provider }` (frozen call sites). `me_worker` may call `platform.list_tenant_ids()`; `me_app`
  may not.
- **Decision:** `ConnectionRef.tenantId` is an optional additive field. The worker resolves the tenant
  by probing `list_tenant_ids()` in one transaction (tenant context per probe, RLS applies), cached per
  process. API call sites pass `tenantId` (one-line edit in `modules/tasksync` preview; my own
  handlers pass it).
- **Consequences:** E4's `admin.checkMapping` (and any other API call site that builds a connector for
  a Jira connection) must pass `tenantId: ctx.tenantId`, or the Jira adapter answers `unavailable`.

### E5-5 · Tokens: AES-256-GCM bound to the row; refresh serialised; failures fail closed
- AES-256-GCM, 12-byte IV per encryption, additional data `tenant|connection|field` (a ciphertext
  copied to another row does not decrypt); `key_id = k1-<12 hex of sha256(key)>`;
  `CONNECTOR_TOKEN_KEY_PREVIOUS` decrypts during rotation, refresh re-encrypts with the current key.
- Refresh before expiry (60 s skew) and once on a 401, under `SELECT … FOR UPDATE` on the credential
  row: Atlassian rotates refresh tokens, so concurrent refreshers would otherwise spend the same token
  and wrongly expire the connection. A refused refresh, a revoked credential or an undecryptable token
  → `token_expired` (connection-level: the outbox pauses sends; S11 shows "Jira connection expired").
- Disconnect wipes both ciphertexts and sets `revoked_at` (`revokeCredential`, ready for CR-E5-1).

### E5-6 · OAuth state
- State = `<connection id>.<32 random bytes base64url>`; only `sha256(state)` is stored; ten minutes;
  consumed by an atomic `UPDATE … WHERE used_at IS NULL` in its **own** transaction before the code
  exchange, so a failed exchange cannot leave it reusable. It must match the tenant (RLS), the
  connection in the path and the admin who started it. The connection prefix lets S14 find the
  connection when Atlassian redirects to the single registered redirect URI (Atlassian requires an
  exact match, so the connection cannot be a query parameter of `redirect_uri`).
- PKCE is not used: confidential client, server-side exchange with the client secret, single-use state
  bound to the admin.
- `completeAuthorization` refuses an authorization missing any of the four scopes, or whose grant
  does not cover the connection's site; records site, cloud id, account, scopes, who and when
  (audit `admin.connection_authorized` — never the code, state or tokens).

### E5-7 · Error mapping (as WAVE4, plus)
401 → `token_expired` (after one refresh); 403 → `permission_denied`; 404 → `validation`;
400 `errors.assignee` → `permission_denied` ("assignee … is not a member of project …", the S11 copy);
400 project/issue type/other → `validation` (field names only, never values); 429 → `rate_limited`
with `Retry-After` (seconds or HTTP date; 5 s fallback); 5xx → `transient`; timeout or reset on a
write → `timeout_ambiguous`; on a read → `transient`. Assignees are resolved to account ids with
`/user/assignable/search`; an assignee who is not assignable fails that task only, before any create.

### E5-8 · Reconnect for Jira
`admin.reconnect` on a Jira connection runs the live health check (which refreshes the grant when it
can). A revoked grant stays Expired (audit `admin.connection_tested`, "a new authorization is
needed"); the admin connects again through `authorizeConnection`. Simulated connections keep the WS1
behaviour exactly. Paused sends resume only through the outbox sweep and its send-time re-check.

## Workflow updates

**WF-07 (task sync)** implemented for Jira Cloud, unchanged in shape:
- Preview: project, issue type, the account's Browse/Create/Assign permissions and assignable users,
  with `problemCodes` (`project_not_found`, `issue_type_not_found`, `assignee_not_found`,
  `assignee_not_in_project`, `permission_denied`). No writes.
- Send: search by key label → create (key property + label atomically) → read back → "Confirmed ·
  PIL-n" with Jira's key.
- New failure paths: *grant revoked / refresh refused* → connection Expired, unsent tasks paused,
  CSV export works, reconnect = new authorization; *token key changed* → Expired until reconnected;
  *Jira dropped the property* → set it, or rely on the label when Edit issues is not granted.

**New sub-flow — connect Jira Cloud (S14):** add site (Expired) → "Connect as integration account" →
Atlassian consent → redirect to `/admin/connections?code&state` → `completeAuthorization` → health →
"Connected · Growth OS integration".

**Known gaps**
- Jira search-index lag right after a create (real Jira only) could hide an issue from a reconcile
  that runs within seconds of a timeout; the outbox backoff (≥ 30 s) makes this unlikely. A stronger
  guard would be a per-connection "recent creates" cache — not built.
- No disconnect endpoint (CR-E5-1). No Data Center support (D-121 §1).
- `health` checks permissions only in projects that already have a mapping.
